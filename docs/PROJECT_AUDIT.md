# home 项目架构与完成度审查

> 这是修改前的审查快照，记录起点为 `813f1ff`。后续实现及最新验证结果请阅读 [交付与验收说明](DELIVERY.md)，以下“当前”均指初始审查时的状态。

本次审查针对 2026 年 10 月 1 日的本地代码、实际 API 网关和 Mars 当前公开官网。结论是：项目已经形成私人关系助理的后端原型，但完整产品的关键流程尚未闭合，而且部分数据保护规则只在抽取管线中成立，Agent 工具可以绕过。优先补数据正确性、对话与摄入流程，再补星图和界面。

审查起点为 Git 提交 `813f1ff`。原有 137 个单元测试全部通过；本次补了 4 个网关兼容测试，总计 141 个通过。真实 API 已验证两轮建档与问答。未跑新的完整抽取评测，也未验证 Mars 登录后的产品，所以不能把旧模型的分数或官网宣传当成当前验收结果。

## 产品方向和对照依据

[Mars 当前官网](https://marsdata.ai) 的公开主线是关系维护、截图分析、长期记忆、可复用 Skill、IM 接入和 Deep Research。当前首页 HTML 标题为关系维护 AI。搜索引擎仍返回旧版直播分析文案，本次以直接获取的当前首页为准。

home 的「以人为索引」定位与当前 Mars 一致。主要差异在完整体验：当前代码把聊天、人物、待确认、星图、提醒、通知、日志和技能做成独立面板，但尚未把一次关系分析连成可追溯、可确认、可恢复的任务流程。

README 的「43/81，约 53%」是此前的需求覆盖统计，不是本次独立验证的产品完成度。原始 PRD 仅引用了旧机器的绝对路径，未在当前仓库及已搜索的 WorkBuddy 路径中找到；无法逐条核实这 81 条需求及 20 条验收用例。

| 能力 | 当前代码实际提供 | 主要缺口 |
| --- | --- | --- |
| 人物档案 | 人物、别名、字段版本、合并拆分、归档恢复、清除 | 同名歧义没有覆盖全部读写入口，字段来源和历史缺少完整展示 |
| 截图与文档 | 视觉转写及 PDF、Word、Excel、PPT、文本解析 | 转写不等于关系洞察；无独立分析结果页，大文件截断和进度体验不完整 |
| 记忆 | 结构化字段、事实、反思、日志、技能，FTS 与可选向量 | 置信度规则不一致，历史业务时间链路不完整，检索没有量化验收 |
| 回复与 Skill | 16 个工具、保存和调用技能、文字问答 | 无稳定的结构化引用、回复教练交互及技能导入导出 |
| Deep Research | 预检索、提案生成、并行子任务、审查和合成 | 提案不能由用户确认；审查没拿到原文；无真正恢复、证据图表和分享 |
| 关系星图 | SVG 圆周排布、关系线、点击查看人物 | 无 3D、分环和研究节点，人物增多后缺少布局和筛选 |
| 首页与任务 | 默认直接进入聊天，通知靠轮询 | 无主动洞察首屏、持久任务中心、取消重试与恢复 |
| IM 和扩展 | 导入聊天记录、联系人和 URL | 无 IM 同步、语音、视频、浏览器代操作和完整 Projects |

## 架构和数据流

代码是 FastAPI 加 SQLite 的本地应用，前端为 520 行的单文件 SPA。`app/` 有 32 个 Python 文件，30 个 `/api/` 路由声明；schema 有 24 个建表声明，其中一个是 FTS 虚拟表。这些数量只描述规模。

| 层 | 关键文件 | 责任 |
| --- | --- | --- |
| 配置和模型 | `app/config.py`、`app/llm.py` | 环境配置、任务模型分层、文本、JSON、视觉与向量请求 |
| API 和页面 | `app/api/main.py`、`web/index.html` | 面板读写与同步调用业务流程 |
| Agent | `app/agent/harness.py`、`tools.py`、`prompts.py` | 拼上下文、最多 10 轮工具调用、生成回答、随后抽取用户文本 |
| 记忆处理 | `app/memory/extract.py`、`apply.py`、`disambiguate.py` | 结构化抽取、凭证校验、身份决策、分项落库和幂等 |
| 检索 | `retrieve.py`、`fts.py`、`vector.py`、`compile_card.py` | 档案卡、名字查找、全文和向量检索 |
| 数据存储 | `app/store/repo.py`、`db.py`、`schema.sql`、`blob.py` | WAL、线程连接、CRUD、内容寻址文件、归档和清除 |
| 摄入和后台 | `app/ingest/`、`app/jobs/scheduler.py` | 转写、文件解析、聊天切块、提醒、日志和周反思 |

一轮聊天的真实顺序是：保存用户消息 → 拼系统提示、人物档案和历史 → 模型调用工具并直接写库 → 保存回答 → 对同一条用户消息做抽取 → 再次落库 → 返回结果和回执。工具写入与抽取写入是两条独立路径，这是重复写入和规则旁路的根源。

摄入流程是：创建 job → 同步解析或转写 → 抽取 → 落库 → 创建互动 → 更新 job → 返回 HTTP 响应。存在 job 表和状态查询接口，但还没有真正的后台任务队列；浏览器不能在提交后立刻拿到任务 ID 来持续看进度。

SQLite 和 blob 存在本地；推理仍需把文本、上下文或截图发送给配置的模型网关。前端「数据不出机器」与实际网络行为不符，应该准确说明本地存储与外部推理的边界。

## API 接入结果和本次改动

用户提供的网关地址已写入被 Git 忽略的本地 `.env`，密钥未进入源码、测试或此文档。已建立 `.venv` 并安装依赖。

`GET /models` 返回 5 个模型：`ZHIPU/GLM-5.3-Flash`、`deepseek-v4-flash`、`deepseek-v4-pro`、`qwen3.7-flash`、`qwen3.8-max`。这只是模型清单，能力需要分别实测。

| 用途 | 本地配置 | 实测和限制 |
| --- | --- | --- |
| 轻量标题与归纳 | `qwen3.7-flash` | 非流式文本请求成功；本次强制工具调用未返回真正的 tool_calls |
| 主循环和抽取 | `deepseek-v4-flash` | 强制工具调用成功，真实两轮建档及问答成功 |
| 分析审查 | `deepseek-v4-pro` | 强制工具调用成功；尚未验证完整研究流程 |
| 报告合成 | `qwen3.8-max` | 未跑完整报告验收 |
| 视觉 | `qwen3.8-max` | 测试图片的颜色识别成功；不是复杂聊天截图的 OCR 质量验收 |
| 向量 | 空配置，明确关闭 | 现有 `/embeddings` 请求返回 HTTP 400 `query is empty`，没有拿到向量；不假定此网关支持项目所需的 OpenAI embeddings 接口 |

发现的兼容问题是：省略 `stream` 时，网关会返回 `text/event-stream`，SDK 得到字符串，原代码访问 `.choices` 时失败。显式传 `stream=False` 后，返回可解析的 JSON。因此在 `app/llm.py` 的文本和视觉调用中补了这一参数。

另外允许空向量模型配置立即报明确信息，避免每次写入、消歧和检索都对不可用向量接口重试。现有业务层会回退到结构化和全文检索。此状态尚未在前端展示，是待补项。`requirements.txt` 加入 `tzdata`，让 Windows 环境可以取得 `Asia/Shanghai` 时区数据。

新增 `tests/test_llm.py` 验证文本和视觉的非流式参数、关闭向量时不请求网关、空输入不依赖向量模型。未改变人物、账本、抽取或研究的业务逻辑。

## 已复现的数据正确性缺陷

以下复现使用内存数据库或 `data/audit/` 的独立测试数据库，不把测试联系人混入正式档案。这里的问题尚未修复。

### 同名人物保护被工具绕过

`app/store/repo.py:39` 的 `get_person_by_name()` 使用 `LIMIT 1`。`app/agent/tools.py:117` 的名字解析及 `save_person_fact` 直接沿用它，没有进入消歧流程。

复现：创建王甲、王乙并都加上「老王」别名。`disambiguate.resolve()` 正确要求确认，但工具保存「老王的城市是杭州」却立即成功，修改其中一个人的档案。承诺、账本和关系边也有依赖单人查找的入口。应让全部读写通过统一身份解析；歧义时返回候选，确认后使用明确 person_id。

### 同一笔账可因两条写入路径计入两次

`tools.record_transfer` 的去重键在无日期时使用 `today`；`apply_extraction` 使用 `occurred` 原值，两者对同一事件生成不同键。

复现：先让工具记录「给张晨 100 元礼金」，再让抽取管线应用同一消息中无明确日期的这笔礼金。预期支出 100 元，实际支出 200 元、两条账。应统一日期归一化和事件标识，并让工具与写后抽取共同使用一次消息的写入记录；不能只测单条管线内部的重放幂等。

### 待确认账目无法在待确认面板处理

`app/memory/apply.py:192` 的普通中置信账本分支直接写 `ledger_entry(status='pending')`，没有创建 `pending_item`。只有部分疑似重复分支入确认队列。

复现：一笔 0.7 置信度、此前没有类似历史的 100 元礼金产生一条 pending 账目，但确认队列中的 ledger 数量为零。它被排除在汇总之外，却没有确认或丢弃入口。应统一待确认工作流及状态转换。

### 低置信事实仍直接进入记忆

`app/memory/apply.py:122` 的 facts 分支不执行字段使用的置信度分档。用户自身 notes 的分支也直接写入；工具字段写入直接给 1.0 置信度，并且 evidence 可以缺失。

复现：0.1 置信度的「喜欢网球」被保存为 episodic，结果标为成功，没有待确认项。应把事实、个人记忆、字段、关系及工具写入都纳入一致规则，并区分用户明确确认和模型自行判断。

### 归档人物的互动仍可被全文检索返回

归档函数给人物和 memory_item 打删除标记，但互动没有同样的可见性过滤。`app/memory/retrieve.py:33` 读取 interaction 时不检查其关联人物是否已归档。

复现：创建只属于一个人物的「归档测试专属秘密」互动，再归档该人物，全文检索仍返回此互动。需明确共享互动的显示规则，并让检索、上下文、提醒和汇总统一遵守归档语义。

## 对话与摄入流程缺陷

| 问题和证据 | 影响 | 建议 |
| --- | --- | --- |
| `harness.run_turn` 先写用户消息，读取历史后又追加同一文本；复现模型收到当前消息两次 | 重复意图、上下文浪费，也可能加重重复工具执行 | 明确历史是否包含当前消息，只送一次 |
| `repo.list_messages` 按创建时间升序再 LIMIT；复现 limit=1 返回最老消息 | 超过 200 或 500 条时，界面和模型会遗漏最新内容 | 先取最新窗口，再按时间还原顺序 |
| 抽取异常变成 failed outcome，但返回值只保留 ok 和 pending；复现错误不可见 | 回答成功时，用户可能误以为信息也已保存 | 持久化并返回所有写入结果，失败要可重试 |
| 首次打开 curConv 为 null，发送前没有创建对话；HTTP 复现为 404 | 新用户直接输入无法开始 | 自动创建首个会话，恢复失效 localStorage，防止并发发送 |
| 前端 `fd.append('me', me)` 发 multipart，后端 `me: str=''` 被 OpenAPI 定义成 query | 用户填写的聊天身份没有被使用，可能影响归属 | 使用 Form 参数并做接口级回归 |
| 文件和 URL 的 duplicate 分支无条件返回 done | 失败任务再次上传可能被当成成功，并阻止重试 | 返回真实旧状态，失败允许重新排队 |
| ingest 状态通常只数 pending，没有统一计入 failed outcomes | 部分落库失败可能被标为 done | 统一任务成功、部分成功和失败的判定 |
| 文件和聊天导入使用 async 路由，但内部执行同步网络与 LLM 调用 | 长导入会占用事件循环，缺少取消和进度 | 提交后返回 job_id，由后台 worker 执行 |
| 模型工具调用和回执主要留在本轮内存，历史接口仅回 user 和 assistant | 刷新后不能完整审计一次回答的写入和研究过程 | 持久化工具轨迹、证据、任务和回执 |
| 前端 Markdown 仅替换粗体和行内代码 | 真实模型返回的表格、报告、引用不能完整呈现 | 使用可靠渲染器和安全链接，配合人物与证据卡片 |

以上最后几项是代码路径审查结论，不代表已经对每个场景做过浏览器操作验收。

## 记忆与研究实现的边界

字段有 `valid_from`、`valid_to` 和 `recorded_at`，但抽取落库通常没有把事实的历史成立时间传进 `upsert_field()`，而是使用当前时间。查询工具也没有完整的按历史日期查看字段入口。因此当前主要是字段版本留存，尚不能据此宣称已完整支持「2024 年他在哪工作」。

身份消歧的注释称四路召回，但 `recall()` 只遍历别名匹配；评分接受语义相似、共同出现和上下文字段参数，主落库调用只传了名字。名字向量和检索模块存在，并不意味着这些信号已经接进消歧。

研究代码有提案、并行和草稿字段，但有三个重要边界。第一，提案生成后直接执行，用户没有确认节点。第二，`_review()` 接收的是结论和 URL，没有源文片段，不能可靠判断论断是否得到来源支持，也没有强制引用必须来自实际抓取集合。第三，草稿只在全部子任务结束后保存，没有恢复入口、每步检查点、取消重试及稳定任务状态机。

网页抓取主要是 HTTP 请求加正则去 HTML，不能替代云浏览器；未检查 HTTP 错误页面是否被当成正文。Bing HTML 搜索的长期稳定性、来源质量、研究报告的事实正确性均尚未验收。不能把这些模块的函数存在视为 Mars 完整研究能力已完成。

提醒依赖应用进程存活和每分钟轮询；没有独立常驻服务或系统级通知。确认待办中的承诺分支没有补建对应提醒和 applied_patch，也需要纳入状态转换验收。

## 建议补全顺序和验收标准

第一阶段先建立统一写入服务。全部入口共用身份解析、证据规则、置信度分档、事件去重和回执保存。验收重点是两个老王不会误写、同一笔 100 元不会变成 200 元、低置信结果有处理入口、归档后不被普通检索和上下文暴露。

第二阶段完成日常使用闭环：首次打开即可开始对话，展示流式回答和真实工具进度，文件提交立即返回任务 ID，长任务可取消和重试，刷新后恢复状态，人物能查看来源及字段历史。用 API 和浏览器端到端用例验收，不以单元测试数量代替。

第三阶段补关系助理的价值页面：首屏展示最近变化、未闭合承诺和适合跟进的人；截图导入后给有证据的关系分析和回复草稿；Skill 有完整编辑及复用流程。星图在这些数据闭环成立后再升级布局和 3D。

第四阶段补 Deep Research 的证据和任务机制：先批准提案，再执行可恢复的子任务；每个结论链接到来源原文，报告和图表只使用可追溯数据，失败明确显示。IM、语音、Projects 和浏览器执行放在其后，根据具体场景和权限设计扩展。

现有 tests 适合作为基础回归。还需增加跨工具与抽取管线的状态用例、检索标注集、HTTP multipart 参数验证以及完整多轮脚本。旧的 tune 和 holdout 成绩来自此前模型，切换到 DeepSeek 后必须重新测量，不能沿用 README 的 0.9667 作为新配置的成绩。

## 本地验证与启动

本次已执行原有测试、网关模型清单请求、工具调用探针、视觉小图探针、独立数据库两轮真实问答、HTTP 启动检查以及上述数据缺陷复现。首页和人物 API 返回 200；首次直接发送到 null 会话返回 404。没有执行完整 Research、复杂截图识别或真实聊天记录批量导入，也没有对全部页面做浏览器视觉验收。
