## 三、holdout 的两个失败（归因）

### 发现一 · `hold-p02`：相对日期「这周五」算成周六（0/3，稳定失败）

- 输入：`老陆说这周五之前一定把尾款结给我。` · `today = 2026-09-30`（**周三**）
- 期望：`due = 2026-10-02`（周五）
- 实得：`due = 2026-10-03`（**周六**），`who/content` 都对 → 只有日期错
- 已用 `python -c "datetime.date(2026,10,2).strftime('%A')"` 复核：10-02 确实是 Friday，**期望没错**

**根因不在模型笨，而在我们喂给它的信息不完整**：`extract_from_text()` 只告诉模型
「今天是 2026-09-30」，**没告诉它今天星期几**，于是模型得自己做星期运算——而 LLM 的星期运算不可靠。

同一个「周五」在两处的表现：

| 用例 | 语境 | 算出的 due | 对错 |
|------|------|-----------|------|
| `hold-p02` | 直说「这周五之前」 | 2026-10-03 | ❌ |
| `hold-p03` | 聊天记录片段里「我周五之前」 | 2026-10-02 | ✅ |

→ **修复方向（一行的事）**：把星期几一起传进去，`今天是 2026-09-30（周三）`。
影响面：承诺提醒会建在错的日期上，直接触发 FR-TIM-02 的提醒功能。

`promise_recall = 0.75` 就是被这一条拖的（4 条期望承诺命中 3 条）。

### 发现二 · `hold-n13`：把角色词「王芳的老公」建成了人物档案（1/3，抖动）

- 输入：`王芳她老公是苏州一家医院的主任医师。`
- 违反 **FR-ID-01**：「我对象」「那个客户」这类角色词不算人名，参照物是 PRD 的验收原文
  「我的对象今天心情不好」不产生新人物记录。
- 抖动：3 次里 1 次只抽出王芳（对），2 次多建了「王芳的老公」这个人物。
- **注意归属是对的**：模型把 `主任医师` 放在「王芳的老公」名下，而不是放在王芳名下——
  FR-MEM-06 的本意（不得把他人特征归档到当前人物名下）**没被违反**。
  真正的违规只有「不该建这个人物档案」。
- 附带观察：模型自造了一个 `family` 字段，而提示词给的字段清单里没有它
  （只有 company/title/city/birthday/phone/email/trait.\*/need.\*）。`sanitize()` 不校验字段名，
  所以这类 schema 漂移会直接落库。**是否要给字段名加白名单，需要拍板**（见第八节）。

## 四、一处用例修正记录（可审计）

`hold-n13` 的 `must_not` 断言在测量后**修过两次**，如实记下来：

| 版本 | 断言 | 为什么改 |
|------|------|---------|
| 初版 | `must_not: ["value:主任医师"]` | —— |
| 第一次 | `["field:title"]` | 初版太钝：`王芳.family` 的值「已婚，配偶为苏州某医院主任医师」**含「主任医师」**，而这是**合法的家属描述**，被误判成违规 |
| 第二次（现行） | `[]` + `max_people: 1` | `field:title` 仍是**全局**检查，会把 `王芳的老公.title` 也算违规——但那恰恰是**正确归属**。实际违规只有「多建了一个人物」，`max_people` 已精确覆盖 |

**关键点：三次修改后该用例仍然失败**（`人物数量 2 超过上限 1`），所以这不是「把用例改到通过」。
该用例继续失败是**正确的**——它暴露的是真缺陷。

顺带暴露评测器能力缺口：`must_not: field:X` / `value:X` 都是**全局**的，
无法表达「**只**检查某个人身上不该有这个字段」。做 attribution 类断言（FR-MEM-06）需要
支持 `王芳.field:title` 这种带人名的作用域写法——列入下一步。

## 六、留出集会被烧掉——下一轮的协议

只要照着 holdout 的失败去改提示词/代码，holdout 就退化成了 tune，它的数字立刻失效。
所以定死这个流程：

1. **本轮**：只测量、只归因（✅ 已完成，见第三、四节）。
2. **下一轮**：按发现一/二修代码与提示词。修完 **`holdout.jsonl` 降级并入 `tune.jsonl`**。
3. **同一轮**：**新建 `holdout.jsonl`（v2）**，重新按 PRD 出题、不看提示词。
   v1 的 26 条已经被「看过答案」，不能再当验收集。
4. 门槛永远只对**当前这版 holdout** 生效。

代价是每轮都要新出题；收益是「泛化缺口」这个数字每一轮都还是真的。

### 从 holdout 反推：A 的修复其实只对了一半

本轮拿 4 条**新词形**的客套用例（提示词里从未列举过）去问代码闸门，结果：

| 用例 | 内容 | 闸门 | 通过靠什么 |
|------|------|------|-----------|
| `hold-n01` | 有空来家里坐坐 | **拦截** | 代码 |
| `hold-n02` | 哪天得空喝一杯 | **拦截** | 代码 |
| `hold-n03` | 那个事回头再说吧 | 放过 | 模型这次听话（脆） |
| `hold-n04` | 改天请你搓一顿 | 放过 | 模型这次听话（脆） |

闸门漏掉后两条的原因很具体：`_PLEASANTRY` 要求命中**动词白名单**
（吃饭|吃|聚|聊|见面|见|喝|约|坐|玩|联系），而「说」「搓」不在里面。

**这直接给出了下一轮的修法**：白名单是错的抽象。
反着做——**命中客套触发词 且 没有任何具体动作/时间**（`_CONCRETE` 已经能判断）→ 判为客套。
即把「动词白名单」从必要条件降级/去掉，`_CONCRETE` 继续负责放行「下次见面把合同签了」这类真承诺。

所以准确的说法是：**A 的修复在 tune 上成立，在 holdout 上"部分成立"**——被代码兜住的才叫成立。

## 八、已知边界 / 待决策

1. **样本仍然很小**。holdout 26 条，其中标 `negative-promise` 的只有 5 条——
   `promise_false_positive_rate` 的分辨率是 **0.2 一档**，「0.0」这个数字由 5 条支撑。
   要更细的结论就得把负样本加到 20 条以上。
2. **`must_not` 没有作用域**（第四节）。attribution 类断言目前写不出来。
3. **字段名无白名单**。模型可以自造 `family` 之类的字段并落库（发现二）。
   要不要加白名单、`family` 是否应该成为正式字段，需要产品决策。
4. **`evidence` 与 `confidence` 正交**：`sanitize()` 只清理伪造凭证、不动置信度。
   「凭证为空的高置信字段」是否该进待确认，仍是**待决策**（上一轮遗留）。
5. **C（字段归位）没有代码兜底**，三处修复里最脆。
6. **`hold-p02` 的日期错会污染提醒**：承诺日期错了，FR-TIM-02 的提醒就错了。

### 已决策（待实现）

- **P5 删除语义**：定为「**归档 + 提供彻底清除入口**」。
  - `soft_delete_person` 现在是软删（只置 `deleted_at`，`person_field` / `person_alias` 行仍在）。
  - UI 口径从「删除」改为「**归档**」（可恢复），另给一个显式的「**彻底清除**」动作做物理删除
    （字段 / 别名 / 记忆 / 账本 / 证据引用 / blob）。
  - 依据是 PRD **FR-ID-02 边界**：「删除一个人时，**别名必须一并删除**」，
    且验收要求「删除后全库搜索该人的任何曾用名返回 0 条；校验不通过要报『部分删除』而不是『已删除』」——
    也就是说产品本来就要求真实删除，只是需要一个显式入口来区分「归档」与「清除」。
  - `tests/test_invariants.py::test_p5_delete_is_physical` 目前是 `xfail`，实现后应转正。
