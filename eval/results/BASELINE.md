## 三、三类缺陷的修法（以及一个不在计划内的第四类）

### A 承诺误判：社交客套被当成承诺（语境敏感）

- **现象**：`extract-n12` 聊天记录片段里的「改天一起吃个饭」、`extract-n11` 的「以后在杭州能常见面」
  被抽成承诺。同样一句话直说时（`extract-n02`）不犯。
- **修法**：两层。
  1. 提示词第 5 条把客套钉死，给出正/反例，并明确「不要因为对话轮次变多、语气变正式就放宽标准」——
     直接对着「语境改变了判断」这个成因说的。
  2. **代码闸门** `_is_pleasantry()`（`app/memory/extract.py`）：命中客套模式且无具体动作/时间的，
     直接从 `promises` 里删掉。**为什么必须落代码**：见第五节。

### B evidence 拼接：模型用「；」把不相邻的原文拼成一条凭证

- **现象**：`extract-p10` / `extract-r10` / `extract-n11` 的 `value_read.evidence` 把两段相隔很远的
  原文用分号拼成一句。它读起来像凭证，实际在原文里根本不存在。
- **修法**：`_evidence()`（`app/memory/extract.py`）做两级兜底：
  1. 整条能在原文里对上 → 原样保留；
  2. 否则按标点切开，取第一段确实逐字出现的（仍是连续片段）；
  3. 都对不上 → **清空**。宁可这条没有凭证，也不留一条伪造的凭证。

- **刻意没做的一件事**：没有顺手把「凭证失效」的条目降置信度。
  `evidence` 和 `confidence` 是两个独立信号——**凭证不可用 ≠ 事实不可信**。
  在 `sanitize()` 里偷偷改分会掩盖模型自身的校准误差，让 `confidence` 这个指标失去意义。
  真要让「无凭证的高置信字段」进待确认，应该在 `apply.py` 加一条**显式**规则，而不是在这里调分。
  这条留作待定项（见第七节）。

### C 语义归类错误：薪资进了人情账本、城市进了 company

- **现象**：`extract-r08`「张伟年薪涨到 80 万」被记成 `ledger`；`extract-r05`「公司搬到杭州了」
  把「杭州」放进了 `company`。
- **修法**：**只改提示词**，新增「字段归位规则」段：
  - `ledger` 只记「钱有没有在你和这个人之间移动」；薪资/奖金/公司规模/营收/融资额/房价/报价**不是账本**。
  - 地点归 `city`，并显式点明「公司搬到杭州了」里的杭州是 `city` 不是 `company`——模型的本能是把它归给公司。

### D（计划外）同字段多值：一次抽取给两条 `city`

- **怎么冒出来的**：修 A/B/C 之后的第 1 轮，`extract-p01` 挂了，报「`city='滨江'` 不含「杭州」」。
  看原始输出，模型**同时给了 `city=杭州` 和 `city=滨江`**（滨江是杭州的区）。
- **真正的问题不在模型**：评测器的 `_fields_of()` 把字段存成 `{字段名: 条目}` 字典，
  **同名后写的覆盖前写的**。也就是说「杭州 + 滨江」两条，谁生效取决于 JSON 里的先后顺序——
  这条用例因此**时过时不过**（复跑 3 次：过、过、挂）。
  这跟本项目 P1 的原则是同一类错误：**不能让一个真实缺陷被一层便利抽象悄悄吃掉**。
- **修法**（两侧都改）：
  - 提示词：一次抽取同一字段只给一条值；同时出现城市与区/街道时 `city` 只取城市层级。
  - 评测器（`eval/metrics.py`）：新增 `_dup_field_failures()`，同一字段多个**不同**取值直接判失败，
    不再依赖覆盖顺序；`_match_field()` 改成「任一取值满足即命中」，消除顺序依赖。

## 四、一次真实的回归：否定式规则让模型少抽了东西

第 1 轮把 ev/pfp 打满的同时，`extract-r07` 从「过」变成「**稳定挂**」（复跑 3 次全挂）：

- 输入：`老路说他门公司要裁员了，让我帮忙留意机会`
- 期望：至少一条含「裁员」的 `facts`
- 实际：`facts: []` ——**整条事实都没了**

原因不复杂：第 1 轮加进去的规则**全是否定式**（「不算」「不是」「不要」），提示词里只有减法没有加法，
模型过度收敛，把该记的事实一起减掉了。`extract-p01` 同期也受影响。

修法是给提示词补**正向配重**（新增一段）：

> 别把「事实」也一起丢掉（上面否掉的是客套和角色词，不是事实本身）：某人单位裁员/搬迁/出事、
> 换工作/升职/结婚/生病/住院/生孩子/搬家——这些是明确发生过的事，即使不涉及金钱、也不是承诺，
> 也必须抽成一条 `facts`。

**教训**：往提示词里加约束时，必须同时给一条「别把对的也否掉」的正向条款；
否则指标会以一种你注意不到的方式好转（ev 上去了，召回下来了）。
注意 `field_recall` / `promise_recall` 这条回归**没有触发任何门槛告警**——是逐条看 `FAIL` 才发现的。

## 五、本轮最有价值的发现：只改 prompt 不够

第 2 轮连过两次 32/32 之后，第三次复跑掉到 31/32，挂的正是 `extract-n11`。原始输出：

```json
{"who": "them", "content": "以后在杭州能常见面", "due": null, "confidence": 0.4}
```

也就是说修 A **没有根除问题，只是改变了它的形态**：

- 修复前：客套被当成**高置信承诺**（0.9）→ 直接写进 `promise` 表 + 生成提醒；
- 修 prompt 后：同样一句被当成**低置信候选**（0.4）→ `apply.py` 按分档扔进「待确认」。

从统计上看 `promise_false_positive_rate` 掉到了 0；从产品上看，用户偶尔还会被问一句
「张伟说以后常见面，这算承诺吗」。**这是「指标达标」和「问题解决」分岔的地方。**

结论：**「客套不是承诺」不是置信度问题，是语义问题**，交给模型自觉就一定会漏。
所以加了代码闸门 `_is_pleasantry()`——和 B 的思路一致：**不指望模型每次都听话**。
闸门带一个反向豁免（`_CONCRETE`），避免误杀真承诺：

| 输入 | 判定 |
|------|------|
| 改天一起吃个饭 / 以后在杭州能常见面 / 回头我联系你 / 保持联系 | 客套 → 丢弃 |
| 下周三之前把报价单发给他 / 9/8 之前给你确认 | 承诺 → 保留（不含客套词） |
| 下次见面把合同签了 / 以后每周五给你发报表 | 承诺 → 保留（含「下次/以后」但有「把…」「周X」） |

> 踩过的坑：`_CONCRETE` 最初把中文数词写成了 `[一二三四五六七八九十百千万]`，
> 结果「改天**一**起吃个饭」里的「一」被判成「有具体动作」，闸门失效。
> 已收紧为「数词 + 量词」（一块、两天、周五…）。

## 六、评测器自身也改了（评估器写错比被测代码错更危险）

`eval/metrics.py` 本轮的三处改动，都配了单测（`tests/test_eval_metrics.py`）：

1. `_flat()` 改为直接复用 `app.util.flatten_for_match()`。
   原来评测器自己维护了一份标点/空白正则，和抽取器**各写一遍**——两边一旦漂移，就会出现
   「评测说 evidence 不在原文，但抽取器认为在」的自相矛盾。现在只有一份实现。
2. `_match_field()` 改成「同一字段有多条时，任一满足即命中」，去掉顺序依赖。
3. 新增 `_dup_field_failures()`：同字段多个不同取值 → 判失败（第四节 D）。

## 七、没做的事 / 已知边界

1. **没做留出集**。32 条全是对着提示词调的，此刻的 1.0 是**调参集上限**，不是泛化能力。
2. **样本太小**：标 `negative-promise` 的只有 4 条，误判率的分辨率就是 0.25 一档。
   「从 0.25 降到 0」这个结论，实际只由 4 条用例支撑。
3. **C 没有代码兜底**。归位（账本/城市）纯靠提示词，属于语义判断，硬规则容易误伤，
   先留在 prompt 层靠评测监控。这是三处修复里最脆的一处。
4. **`_is_pleasantry()` 是中文模式匹配**，对「下次见面聊聊方案」这类**既像客套又像真事**的句子
   只能取一个倾向。它解决的是已知的客套词形，不是理解。
5. **待定（需要产品决策）**：「凭证为空的高置信字段」是否应该在 `apply.py` 进待确认？
   （见 B 那节的说明。目前**没有**采用降置信度，保持 evidence 与 confidence 正交。）
6. **待定（上次遗留）**：P5 删除语义——`soft_delete_person` 只置 `deleted_at`，
   `person_field` / `person_alias` 行仍在。物理删除还是「归档 + 彻底清除」，需要拍板。
   `tests/test_invariants.py::test_p5_delete_is_physical` 目前是 `xfail`。

## 八、下一步（按性价比）

1. **补留出集**：新写一批用例，**不许回头改提示词**。这是当前唯一能把「1.0 是上限还是能力」
   分开的办法。建议把现有 32 条拆成 `tune.jsonl` / `holdout.jsonl` 两半，门槛只对 holdout 生效。
2. **引入重复采样（k=3）**：现在每条只跑 1 次，`pass_rate` 会把「偶发」和「稳定失败」混在一起。
   跑 3 次取最差，才是可信数字。（本轮 A 的偶发性就是这么发现的。）
3. **补 L3 检索层 / L4 端到端层**（见 `eval/README.md`）——目前只有 L1 抽取 + L2/L5 免费层。
4. **给 C 加监控**：为「薪资进账本」「城市进 company」各写一条专门的负向用例，
   在提示词漂移时第一时间报警。
